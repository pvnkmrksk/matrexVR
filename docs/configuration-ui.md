# Unity experiment studio

## Operator overlays and their saved locations

Open **Configure → Operator display & monitoring → Overlay placement & configuration file**. The read-only path is the exact system JSON file being edited. Each overlay also shows its JSON location: `$.statusOverlay`, `$.frameOverlay` or `$.desktopControls`.

Overlays default to automatic placement. Disable **Automatic placement** to enter preferred X/Y positions in physical display pixels measured from the bottom-left. X/Y fields are gray while automatic placement is on; disabling the overlay grays its other controls without deleting their saved values. Output display indices start at 0. Desktop controls may use display −1 to follow the first desktop-preview rig.

The allocator protects calibrated LED rectangles and keeps monitoring widgets apart. A preferred location relocates if needed; an exact free strip remains usable even without decorative margins. If no free rectangle fits, the monitoring widget hides rather than covering an LED stimulus. Fullscreen monitor previews permit operator overlays because the view occupies the full screen. An explicitly opened frame-rate settings dialog can temporarily overlay a full display when no free area fits.

**Rendering & timing → Stimulus resolution** defaults to 1920 × 1080 for a fullscreen monitor rig on the main output. Select **Native monitor**, another preset, or **Custom** and enter a width and height. Setup uses the monitor's native size. Calibrated LED layouts keep their native pixel rectangles, and secondary outputs use their system display modes. A fullscreen render with a different aspect ratio can leave bars around the stimulus.

The overhead preview uses `$.overheadCamera` in the same system JSON. Its X/Y/width/height remain normalized fractions of the display, and it uses the same LED-safe allocator. These settings move operator graphics only; physical camera rectangles retain the apparatus calibration.

Run status and frame-rate readouts use routed canvases; desktop controls use a routed UI Toolkit panel. A connected secondary display is activated when explicitly selected. An unavailable display produces a warning and falls back to operator display 0. The temporary live frame-rate editor uses Unity IMGUI on operator display 0; `frameOverlay.targetDisplay` routes the readout, not that settings dialog.

The Config UI Test integration provides a working runtime UI Toolkit experiment studio to `ControlScene`. Experiment execution remains inside the Unity player; Python plotting and analysis remain optional. A desktop Unity release includes the UI and its JSON schemas without a Python installation, uv, browser server, or second application.

## Try it

In Unity 6000.3.16f1, choose **Tools → Experiment setup → Open setup screen (Play)**. This opens `ControlScene` and bypasses auto-start for this preview without editing any configuration file. Leave Play mode to end the preview.

Normal players honor the sequence's existing `autoStart` setting. Ship `autoStart: false` for a release that opens setup on double-click. `-configure` overrides auto-start when launching an existing player; `-no-configuration-ui` disables the studio for legacy validation workflows.

An unconfigured apparatus opens a clearly labelled **Night sky** flying demo; press **Start demo** without hardware. **Configure** holds species, walking/flying mode, VR/display counts, LED dimensions, face order and tracker endpoints. Its face net and display map share the runtime pixel geometry. Save with **Use this configuration**; subsequent sessions put the sequence and block parameters first, retaining hardware settings separately.

Choose LED panels or monitors with the two output icons. Set the VR count with one numeric field; changing the count preserves the retained rigs' calibration. The MATRIX brand opens a quiet About dialog with design credits, the source repository and license notices.

**Initialize tracking** opens the independent native tracker windows while setup stays open. Check input and calibration before **Start experiment**; initializing does not start the experiment or allocate a run directory. Per-rig **Save tracker video** and **Recorder control** select automatic experiment recording or explicit manual/external recording. Automatic recording attempts owned native endpoints and reports acknowledgement or unavailability. Missing trackers or video produce warnings while the VR continues. Manual leaves start/stop with the operator.

Use **Tab / Shift+Tab** to move between controls, **F1** for shortcut help, **Ctrl/Cmd+S** to save, and **Ctrl/Cmd+Shift+J** to open the current JSON. **Alt+1–5** selects Start, Sequence, Experiment settings, Recordings and Apparatus. Tab stays inside an open dialog. Escape closes dialogs or returns to Start; an unapplied JSON draft stays visible for applying or discarding.

Session cards hold experiment name, experimenter, comments and each animal's arbitrary text ID. Species is read from system `speciesName` and changed in **Configure**, then copied to metadata `SpeciesName`. Sex starts at **Unspecified**, and an empty age remains unspecified. Each subject has its own comments, with starvation details behind the subject settings icon. These values are saved in `AnimalMetadata.json` with the run and reloaded when returning to setup; a transitional `FlyMetaData.json` copy supports old analysis. Hardware rig IDs remain the system's routing keys; the animal's Animal ID is its free-text label. Existing metadata extension properties are retained.

**Auto start**, **Loop** and **Shuffle** are labelled checkboxes with Lucide icons. They edit the original sequence flags and are also visible in the sequence editor. Auto start controls the next launch; the current setup session starts with **Start experiment**. A clickable system strip shows tracking modes, panel count/resolution/order, tracking input addresses and telemetry output. A compact virtualized **Coming up** list shows the current sequence, effective block timing and a stimulus summary. Longer plans scroll within that list.

The header opens **Sequence config**, **System config** or **Experiment configs**. The last lists only referenced files in the current sequence, with the number of blocks using each. **Session** returns to the simple screen while retaining unsaved labels, notes and config edits. Detailed editors expose full settings; **More → All parameters / Edit JSON** provides the complete document tools without putting them on the landing screen.

In **Sequence config**, blocks are virtualized cards showing their config path, environment, exact effective timing and stimulus/movement summary. Use the native drag handles to reorder, the copy icon to duplicate, or the bin icon to remove a block. Click a card for its environment, outer duration, gain, auto-trim and reload controls. Gain sliders span **0–50**; exact text entry also accepts negative or larger values without slider clamping. A phased config owns its timeline, so the retained outer duration is visibly disabled in the builder; it remains editable under **All block settings** or JSON.

**Add experiment block** opens a searchable file library. Filter by paradigm, inspect timing/effects and phase states, then add the selected complete config in one action. Current configs, templates, examples and custom JSON are listed. The **Archive** category loads historical files on demand. A custom relative or absolute JSON path can be loaded from the same dialog. System and sequence files are excluded from individual block selection. The environment is suggested from the file and remains selectable from the compatible scene family. Replacing a block changes its scene/reference while retaining existing gain, duration, reload/trim flags and extension fields.

**Edit config** opens the referenced document directly. Essentials exposes common controls; Motion, Stimulus, Sky and Tuning group the rest on the same page. Pre/stimulus/post phase tabs show their on/off state and duration. Missing optional phases are displayed without adding JSON; the explicit Add action creates them. Enabling a phase with an omitted duration inserts its displayed 10-second authoring default so it can run. Disabled phases keep their values. Native vector icons, illuminated ON/OFF switches, XYZ controls, color swatches and sliders make values visible. **All parameters**, **All fields**, and **JSON** retain access to every stored and schema-defined setting, including extension keys.

Number entries retain their exact JSON text. Sliders are convenience ranges and never clamp a value simply by displaying it. Numbers outside a slider's range remain editable and visibly marked. Explicit slider changes use a documented step and synchronize the exact entry. Pending slider positions flush before navigation, undo, save and Start. Ports, IDs and values without meaningful slider ranges retain number entries.

The frame-rate cap defaults to **60 FPS**. Click the cap readout to open its exact setting. Saving a cap or VSync change in setup applies it immediately while idle. During an experiment, the readout opens a small live cap editor; applying a cap keeps acquisition running and appends a timestamped `runtime_display_settings.jsonl` event without rewriting the archived initial configuration. VSync disables an ineffective live cap edit.

The run overview shows exact total timing, heading-assessment time, loop/order state and effective config effects. Sky summaries follow uniform-color/panorama/procedural precedence and distinguish live from fixed sky. Disabled or absent phases are marked inactive. System overview shows input modes, frame synchronization, display, configured camera faces, telemetry and overview state. Configs shared by multiple blocks are explicitly labelled.

**Make an independent copy** on a selected sequence block creates a complete variation file and relinks only that block. Undo restores the original reference; the newly created file remains on disk. **Save a variation** in the sidebar copies the current document. Existing files are never overwritten by these creation actions. Absolute paths are supported; relative experiment/data references resolve against `RuntimePaths.ConfigRoot` (Editor: StreamingAssets; standalone: writable profile), matching the runtime loaders. **Open a file** loads a different primary system/sequence or standalone config.

**Edit JSON** exposes the complete document. Apply a draft to synchronize the form, or discard it. An unapplied draft blocks navigation, save and start. **Save changes** enables when configuration or session metadata changes, including an edit still in a delayed text field, and disables after a successful save. It commits pending field values, writes changed loaded documents and a metadata draft under `RunData/Backup`, leaving completed-run metadata intact. **Start experiment** validates the active file graph, saves changes, archives a fresh session using the selected system and sequence paths, copies metadata into that new run folder, and starts the existing runner. Session metadata includes every configured VR even when subject details were not edited. Non-looping runs started here return to session setup; Escape also returns from a running experiment. The next run gets a separate data folder.

## JSON parity

The editable source of truth is a Newtonsoft `JToken` tree, rather than a deserialized C# config object. Unknown properties and arrays remain editable. Exact number lexemes are retained, including long integers, scientific notation and decimal values beyond floating-point precision. Numeric controls use delayed text commits to avoid float-widget coercion. Missing, null, false and zero are distinct values. Removing a property restores omission; the ∅ button sets an explicit null.

Missing settings show their declared runtime defaults immediately. Invalid known values show default controls with a **Check JSON** marker while validation continues to block starting. **More → Effective JSON & defaults** shows a read-only resolved document and can copy it or explicitly make those defaults part of the editable draft. Merely viewing defaults never writes them into a source file. Optional phases are not created by this view.

A whitespace-only file opens with inherited defaults and becomes valid `{}` JSON when explicitly saved. Malformed JSON keeps its exact source for repair in **Edit JSON**, while the form remains available for inspecting defaults. It cannot be saved or run until an explicit JSON repair is applied. The normal `.bak` retains the previous malformed input after repair.

A save with no value changes preserves the original bytes, including BOM, indentation, whitespace and line endings. Edited files use pretty-printed UTF-8 JSON with the original property order and preserved untouched numeric lexemes. Whitespace is not preserved after an actual edit. Duplicate property names and nesting deeper than 128 levels are rejected explicitly rather than silently losing data. Known parameters must fit their runtime types before starting; arbitrary extension numbers are preserved without being interpreted as experiment settings.

External changes are checked once per second while setup is active. Clean documents reload into the form. A changed file with an unsaved local edit produces a conflict and cannot be overwritten. Copy the draft from the JSON view before using **Reload disk**. Each file is replaced atomically with a `.bak` of its previous version. Saves across multiple files are not a filesystem-wide transaction. Undo/redo keeps the latest 32 editing transactions. A block reorder is one transaction and moves the complete JSON object, including unknown fields.

## Schema and extension points

`Assets/Resources/ConfigurationUI/schemas.json` contains JSON Schema Draft 2020-12 documents for system, sequence, Choice, Swarm, Kannadi, Optomotor and Dynamic Choice. `ConfigurationSchemaBuilder` generates definitions from the Newtonsoft serialization contracts used by the runtime loaders, including inherited fields, converter unions, private Dynamic Choice types, and shared phase/auto-trim fields. It regenerates before a player build; use **Tools → Experiment setup → Regenerate JSON schemas** after changing config types.

The runtime validator implements the keywords emitted by the generator: `type`, `enum`, `required`, `properties`, `items`, `minItems`, `minimum`, `maximum`, `exclusiveMinimum`, and permissive additional properties. It also runs the existing production validators for cross-field rules. It is not a general-purpose validator for arbitrary third-party JSON Schemas.

The generator's `x-ui` annotations define conditional visibility, enablement, help text, units and soft slider ranges. Compound enable rules cover pose reset plus random-heading conditions. Per-rig poses do not inherit nonexistent sibling flags. Current examples include:

- Kinefly/FicTrac input and flight terrain fields; walking ball diameter hides in Kinefly mode.
- Disabled phases, manual controls, telemetry, overview and sky blocks grey their dependent controls while retaining their enable switch and saved values.
- Autopilot and animation dependent settings; software FPS cap under vSync.
- 2D/3D swarm elevation, scene/Bogong visuals, dot/moth dimensions, world/angular sizing, recorded playback, and continuation controls.
- Auto-trim and flight-check tuning; time/area Dynamic Choice triggers.

Inline Swarm/Kannadi sequence overrides use their scene's field definitions and conditional rules. Autopilot and heading settings stay owned by the experiment file, as required by the current loaders. Changing modes hides controls without deleting values. Disabled contents remain accessible in JSON.

To add an ordinary parameter, add it to the relevant runtime config type and regenerate schemas. Existing scalar/container renderers handle it automatically. Add optional annotations in `ConfigurationSchemaBuilder.Annotate` for mode-specific rules or units. For a new scene/parser, register its schema type and extend `ConfigSchema.ForScene`; keep loading and validation aligned with that parser.

## Performance and scope

The sequence board, landing-screen plan and file library use fixed-height virtualized `ListView` cards. The board supports native reordering. The full-field editor also mounts only visible rows. Nested objects/arrays render when opened. There is no workbench `Update` method. At start the `UIDocument` is disabled immediately and its scene-owned host and `PanelSettings` are destroyed; there is no configuration form, polling, or binding during the run. Setup is recreated only on return to `ControlScene`.

Operator graphics suspend while setup is open. Tab retains setup field navigation and hides/restores runtime status, FPS, overview, desktop controls and replay controls together during a run. Calibrated LED rectangles are reserved against status/FPS/overview placement; a panel is omitted when no free area fits. Diagnostics and optional telemetry keep their separate runtime lifecycle.

The UI and JSON arrays support configurable rig/sequence counts. Current source provisions configured rigs from authored scene templates before their tracking components start, and disables absent rigs. Each isolated population consumes a Unity rendering layer; exceeding the available layer capacity produces a configuration error. Hardware IDs remain `VR` followed by a positive integer. See the 0.3 release verification for tested scene/count combinations. Versions 0.1/0.2 retain the authored VR1–VR4 engine limit.

Current desktop source uses `RuntimePaths.ConfigRoot` and `RunDataRoot`: a writable user-profile Config directory, and a recording library beside each installed player (`MATREX VR RunData` beside the Mac app). Read-only installations use a stable per-installation profile fallback. The Editor uses StreamingAssets and Assets/RunData. Seeding copies missing files and never overwrites a user config. `--config-dir` and `--data-dir` choose explicit roots. Versions 0.1/0.2 retain application-relative storage. WebGL/mobile storage, hardware display calibration and physical tracker timing remain outside this workflow. File selection uses an in-app path field/catalog rather than a native OS file dialog.

## Stable forms and edit-time previews

For Kannadi groups, **Basics → Population and spawn** shows count, appearance, and X/Y/Z spawn offsets on each group card. **Advanced list** opens the same group data for detailed editing. **Load → Kannadi · centred stock swarms** opens repeatable 64- and 206-locust presets with a 68 cm spawn area inside a 72 cm periodic boundary. The camera is 1.6 cm above the planar spawn surface and its far clip is 60 cm. Existing experiment files retain their authored values.

The experiment editor has four conceptual tabs: **Basics**, **Appearance**, **Motion** and **Advanced**. Basics keeps duration and tracking controls together. Appearance groups each object’s built-in choice or external **Custom GLB** path, color override and rendered preview; position, size, animation and surface details are explicit disclosures. Population GLBs use the same compact color controls, while procedural Bogong visuals retain their own appearance settings. Motion groups movement and optional pose/reset controls. Advanced holds visibility, tuning and complete parameter access. The editable human-readable title and relative JSON path share a compact header; the notes icon opens configuration comments.

Apparatus setup starts with VR count and output icons. Display layout, connections and LED calibration remain available behind named disclosures. Numeric stepper buttons fit inside their fields. In the player, the color swatch opens a hex/channel dialog with its Apply action visible at the tested desktop sizes. The right-hand block inspector appears only for the sequence editor when space permits.

Changing a value or enabling a feature updates the existing controls in place. Inactive settings remain gray and retain their saved values. Repeat-from and explicit-seed fields keep their positions when their modes change; monitor output keeps LED calibration visible and restores the saved face order when returning to LED output. Per-display legend rows scroll inside a fixed-height slot, so adding rigs keeps the first calibration card in place. Apparatus editors reserve a 32px input with fully visible text. Save, Start and recording status have reserved geometry. Expanding a parameter disclosure, adding/removing items, selecting a tab or resizing the window deliberately changes the displayed structure.

Booleans use checkboxes. Named enums use dropdowns even when existing JSON stores numeric enum values; changing a numeric enum retains that representation. Schema booleans stored as historical 0/1 flags display as checkboxes and are normalized to the declared boolean type when edited. Exact numbers, unknown JSON fields and pending text edits retain the shared lossless editing workflow.

At Full HD, **Show previews** puts rendered objects and sky images alongside their settings. An imported GLB can retain its own mesh and embedded texture or use a named base-color replacement. Choose **Edit variants** to name local PNG or JPEG files. The picker offers **Original** and the configured names. Preview uses the selected variant immediately. Acquisition loads the images before starting the trial and archives the exact bytes for replay.

**Appearance → Sky & light** supports the default sky, uniform color, a local panorama, and an observer/time-based star sky. Choose a 2:1 image with the native file picker for a custom panorama. Panorama and night-sky thumbnails show the complete 360° image. The experiment renders the configured source at its own resolution. Object thumbnails use visual copies of the selected model and can sample an embedded animation pose.

Thumbnails are 256 pixels wide. They render one visible pane at a time, release obsolete images, cancel pending GLB imports on navigation or Start, and pause during acquisition. They copy transforms, meshes, skin/bone bindings and materials without activating experiment MonoBehaviours, trackers, physics or recording writers. Preview imports read source files without modifying them. Preview decoding is limited to 64 MiB per file; this thumbnail limit does not reject a larger experimental asset.

The build automatically generates lightweight per-asset visual aliases and retains both stock sky shaders. Source-editor users can refresh them with **Tools → Experiment setup → Refresh available choice objects**. The alias catalog stores individual resource keys, so opening one object picker does not load the complete Kannadi prefab collection. Generated aliases are build artifacts.

**Advanced → Who sees whom** contains the optional observer/target matrix. It always reserves 16×16 checkbox cells; inactive VR entries remain gray. Enabling the feature or changing a cell retains geometry and keyboard focus. Disabling it restores the normal scene visibility policy.

## Validation

`ConfigurationUIValidation.Run` requires a disposable project with `KANNADI_VALIDATION_COPY` at its root. Run graphics-enabled Unity with `-batchmode -projectPath <copy> -executeMethod ConfigurationUIValidation.Run -logFile <log>` without `-quit`; the runner exits after its asynchronous checks.

The suite checks every leaf of all current templates/examples, byte-identical no-op saves, raw/form round trips, numeric precision, external conflicts, conditional controls, 10,000 sequence rows, actual UI callbacks and rendering, selected non-default paths, metadata capture, and two complete experiment transitions. The [base validation report](configuration-ui-validation-results.json) covers the full-field and archive checks. The [studio validation report](configuration-studio-validation-results.json) also records session defaults, icon button state, navigation persistence, metadata extensions, dashboard suppression and actual Input System Tab presses, alongside library insertion/custom paths, native drag events, duplicate/remove/replace/variation/undo, numeric controls, absent phases, 10,000 block cards and repeated run teardown. [Session preview](images/config-ui-session.png), [sequence preview](images/config-ui-studio-sequence.png), [settings preview](images/config-ui-studio-settings.png), [system preview](images/config-ui-studio-system.png), and [library preview](images/config-ui-studio-library.png) are rendered by the actual runtime panel using synthetic validation sequences. `ConfigurationStudioValidation.Run` uses the same disposable-copy marker and invocation pattern.

Unity's existing editor search-indexing exception is excluded by its specific stack trace; runtime UI/experiment errors fail the suite. The config-template checker and run-archive regression suite are also run. Runtime UI Toolkit input integration follows [Unity's runtime event-system guidance](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-support-for-runtime-ui/uie-render-runtime-ui/uie-runtime-event-system).
